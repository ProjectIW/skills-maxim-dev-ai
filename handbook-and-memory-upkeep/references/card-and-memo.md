# Карточка проекта и памятка разработчику

## Выжимка аудита в карточку (ориентир – до 600 знаков)

```
[ДД.ММ.ГГГГ], v[X.Y.Z]: готовность [N]/100 ([±Δ] к [ДД.ММ]).
Использование [И], код [К], эксплуатация [Э].
P0: [пункт 1]; [пункт 2] (или «нет»).
Вердикт: [мягкий старт / пилоты / массовый запуск].
Ждёт решения: [1–2 вопроса к владельцу продукта].
Отчёт: [имя файла], не публиковать.
```

Проверь длину: `printf '%s' "$TEXT" | wc -m`. История прошлых аудитов в карточку не копится: она в handbook и памяти.

## Как править карточку (если она хранится в базе)

1. Получи согласие владельца продукта.
2. Сохрани копию записи до правки: `[ПАПКА_КОПИЙ]/project[ID]_before_[ДАТА].json`.
3. Правь одной транзакцией, SQL файлом через stdin (кавычки в командной строке ломаются).
4. Прочитай запись после правки и сверь.

## Памятка второму разработчику при смене выкладки

```
Что поменялось в выкладке [ПРОЕКТ] с [ДАТА]

Коротко: [одна фраза – например «выкладка теперь одной командой, скрипт сам ждёт простоя и делает откат»].

Как выкладывать сейчас:
1. git fetch; убедись, что твой коммит поверх origin/main и номер версии свободен.
2. [команда проверки без выкладки, например bash tools/deploy.sh --dry-run]
3. [команда выкладки]
4. Проверь версию: curl -s [HEALTH_URL]

Чего больше не делать:
– [старый скрипт / ручной rsync / пересборка всех сервисов]
– копировать файлы на сервер руками.

Если скрипт отказал:
– «идёт чужая сборка» – подожди, не запускай вторую (две сборки одновременно могут уронить сервер по памяти);
– «есть активные обработки» – выкладывай позже или с ожиданием;
– в пробном прогоне строки deleting с чужими файлами – стоп, git fetch и rebase.

Откат: [команда].
Вопросы: [кому].
```

Попроси владельца продукта передать памятку и подтвердить, что разработчик её прочитал. До подтверждения перед каждой своей выкладкой проверяй, не выкладывал ли он старым способом (файл с выложенной ревизией на сервере, история контейнеров).
